# Prompt for a recurring Codex task

```text
Open X in the available signed-in Mac browser and search the latest posts with the query `(\"MiniMax H3\" OR \"Hailuo 3.0\" OR \"MiniMax-H3\") filter:native_video -filter:replies`. Discover original MiniMax H3 / Hailuo 3.0 video examples from the last 24 hours and follow docs/DISCOVERY_WORKFLOW.md exactly. Automatically process clear cases whose original post explicitly identifies an H3-generated native video, has a clear author/source and playable media, and is not an obvious repost, bulk advertisement, tutorial/news clip, or unrelated output. Deduplicate against `.review/candidates.json` and public cases. For every clear case, review the actual video and write a concise bilingual content title and summary describing the visible subject, central action/event, or clearly evidenced experiment. Store these under `editorialCopy` with an evidence basis. Never put `@handle`, MiniMax H3, source, date, generation mode, or templates such as “社区视频案例 / 本地生成案例 / Model Comparison by @handle” in a public title; author handles belong only in attribution fields. If the caption does not establish the depicted content, inspect at least beginning, middle, and end frames; if reliable content evidence is still missing, keep the item in the private candidate queue and do not invent copy. Copy prompt text only when the original source post visibly publishes the complete exact text; otherwise record `prompt: null` with provenance `not-published`. Never generate, complete, translate into an alleged original, rewrite, adapt, reconstruct, reverse-engineer, summarize, or decompose a missing prompt, and never infer a hidden workflow from the finished video. Use `mimo-v2.5-pro` only to classify public text and metadata when the local `MIMO_API_KEY` is configured; use `mimo-v2.5` only for limited eligibility/media verification of ambiguous videos. Keep all bucket/API credentials server-side and never print or commit them. Publish through the private transaction pipeline only: run `npm run promote -- --apply`, capture its `.review/publish-staging/{runId}.json` path, run `npm run mirror:videos -- --apply --staging <path>`, then run `npm run commit:staged -- --apply --staging <path>`. Failed items remain private with a factual reason; no case may enter `data/cases.json` before its poster exists and its video passes both checks: the app `/media/{id}.mp4` route returns 307 with a Location header, and a `Range: bytes=0-1` request to that short-lived URL returns 206 with Content-Range. Never print or persist the signed Location URL. Run privacy scanning, validation, tests, lint, Skill checks, and the production build; after success commit and push the related public changes to GitHub, allow Railway to auto-deploy, and repeat the two-hop video check. Report published cases, remaining ambiguous items, public-prompt count, commit, and deployment status. If X is unavailable or logged out, report the blocker without inventing cases.
```

If mirroring reports a mixed batch, still run `commit:staged` for the same manifest so verified entries can publish and failed entries can remain private.

Before open search, process the locally configured private creator queue without exposing its status, scores, outcomes, cadence, discovery labels, or notes. Creator follow-up must never eliminate open keyword discovery and must obey every public eligibility, Prompt, attribution, hosting, and playback rule above.

Before the normal validation sequence, run `npm run sync:stats`. This refreshes the public creator catalog, canonical statistics JSON, public website snapshots, and both README summary blocks; validation must fail if any of those values diverge.

All review status, notes, search queries, discovery sources, rejected IDs, author-radar state, staging manifests, and media failure details belong only under ignored `.review/`. Run `npm run privacy:scan` before and after the production build. A privacy finding blocks publication.

The publication path must set ISO `addedAt` when a case first enters `data/cases.json`. Later Prompt recovery, copy edits, engagement refreshes, or review changes must preserve that original value so they do not appear as new catalog entries.

When public cases, complete Prompts, ranked creators, or first-screen content change, finish the production build and then run `npm run screenshots:capture`. This reuses that build, writes measured build sizes into both READMEs, refreshes the bilingual opening screen and current collection/creator views, and skips byte-identical or visually equivalent images. Run it a second time when changing the screenshot pipeline itself; the immediate repeat must report `0 files changed`. Use standalone `npm run screenshots` only when no current production build exists.
